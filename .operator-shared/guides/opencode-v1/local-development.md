# OpenCode Local Plugin Development

Last Updated: September 15, 2026

## Problem

OpenCode treats a direct local file URL and an npm package as different plugin identities. Configuring both loads both server plugins; TUI duplicate-ID handling instead keeps the first. Hook order therefore cannot safely make `./packages/opencode/dist/index.js` override `@aerovato/operator-opencode`.

## Recommended Registration

Register development builds with a package-qualified absolute file dependency:

```text
@aerovato/operator-opencode@file:/absolute/path/to/packages/opencode
```

OpenCode treats this as the npm package identity `@aerovato/operator-opencode`, so normal config deduplication removes the global `@latest` registration when the development spec is declared in higher-priority project config. Its npm cache installation links to the local package, so rebuilding `dist` and restarting OpenCode applies changes. The plugin's native updater ignores this non-`@latest` cache wrapper.

The repository uses `bun run preview:opencode` to generate `.opencode/opencode.json` and `.opencode/tui.json` with the package-qualified absolute path. OpenCode selects the matching server or TUI package export from the same spec. The generated machine-specific files are ignored.

The repository uses `bun run install:opencode` to build and globally register the local package through OpenCode's forced plugin installer, which detects and configures both exports:

```text
opencode plugin '@aerovato/operator-opencode@file:<absolute package path>' --force
```

Keep this registration project-local so a later global npm install remains lower priority. Generate local config because the required absolute path cannot be committed portably. Direct-file plugin registrations must not coexist with it, or both local identities will load.

## Constraints

- A plain file path cannot suppress the npm package because file URLs deduplicate only against the exact same file URL.
- `bun link` does not affect OpenCode's isolated package cache.
- Replacing or symlinking OpenCode's cache internals is possible but brittle and should not be used.
- A project npm declaration has higher priority than a global development declaration; project-local development configuration avoids that inversion for this repository.
- Restart OpenCode after rebuilding because imported plugin modules are process-cached.

## Global Replacement

A globally registered package-qualified local spec is replaced by any successful global OpenCode plugin installation for the same package when it uses `--force`. `operator-helper install opencode` does this: it clears only the `@latest` cache wrapper, then runs the global forced installer for `@aerovato/operator-opencode@latest`. The obsolete local cache wrapper may remain but is no longer configured or loaded.

Without `--force`, OpenCode recognizes the matching package identity but leaves the existing local spec unchanged. Clearing a cache alone never changes configuration. The native plugin updater also ignores local wrappers because it only updates the exact `operator-opencode@latest` wrapper.

The project-local spec generated by `preview:opencode` still wins inside this repository after any global replacement because project config has higher priority.

## Relevant OpenCode Behavior

- `<reference>/opencode-v1/packages/opencode/src/config/plugin.ts` deduplicates npm specs by parsed package name and file specs by exact URL.
- `<reference>/opencode-v1/packages/opencode/src/config/config.ts` applies global config before project config.
- `<reference>/opencode-v1/packages/opencode/src/config/tui.ts` applies the same global-before-project ordering for TUI plugins.
- `<reference>/opencode-v1/packages/core/src/npm.ts` supports package-qualified absolute `file:` dependencies in isolated cache wrappers.
- `<reference>/opencode-v1/packages/opencode/src/cli/cmd/plug.ts` and `src/plugin/install.ts` detect package exports and patch server and TUI config.
